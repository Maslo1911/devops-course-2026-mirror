# Сравнение Git и SVN — ответы на вопросы

## 1. Почему в Git ветвление «дешёвое», а в SVN — «дорогое»?

В Git ветка — это просто указатель (ссылка) на конкретный коммит, весом в несколько байт. Создание новой ветки — это по сути создание файла с одним хешем коммита, операция происходит мгновенно и полностью локально, без обращения к серверу. Никакие файлы проекта при этом не копируются.

В SVN ветка реализована иначе: физически это копия всего дерева каталогов проекта (`svn copy trunk branches/my-branch`) в репозитории. Хотя SVN использует «дешёвое копирование» на уровне хранилища (copy-on-write, чтобы не дублировать данные сразу), сама операция создания ветки всё равно:
- требует обращения к центральному серверу (нельзя создать ветку офлайн);
- создаёт отдельную «физическую» директорию в дереве репозитория;
- при дальнейшей работе (особенно слияниях) SVN должен отслеживать историю изменений по путям файлов, что исторически было медленным и часто приводило к конфликтам.

Поэтому в Git ветвление — это лёгкая, мгновенная, локальная операция, а в SVN — более «тяжёлая» операция, завязанная на сервер и на структуру каталогов.

## 2. Можно ли в SVN сделать коммит без интернета? Почему?

Нет, нельзя. SVN — централизованная система контроля версий (CVCS). У неё есть один центральный репозиторий, и операция `svn commit` отправляет изменения напрямую на сервер. Без соединения с сервером команда `commit` завершится ошибкой, потому что:
- локально у клиента SVN хранится не полная история проекта, а только «рабочая копия» (snapshot) текущей версии плюс минимальные метаданные;
- нет локального объекта репозитория, в который можно было бы зафиксировать изменения;
- нумерация ревизий и вся история версий ведётся централизованно на сервере.

Для сравнения: в Git коммит — это локальная операция, потому что у каждого разработчика есть полная копия репозитория со всей историей. Интернет в Git нужен только для `push`/`pull`, а не для самого коммита.

## 3. В каких сценариях SVN до сих пор может быть предпочтительнее Git?

- **Большие бинарные файлы и монолитные репозитории.** SVN поддерживает частичную выгрузку (`svn checkout` конкретной поддиректории) и не хранит полную историю на каждой машине, поэтому лучше подходит для очень больших репозиториев (гигабайты бинарных ассетов: игровые движки, CAD-файлы, дизайн-макеты), где клонирование всей истории Git-репозитория было бы неэффективным.
- **Жёсткий централизованный контроль доступа.** SVN позволяет настраивать права доступа на уровне отдельных папок/файлов в репозитории, что удобно в организациях с строгими требованиями к тому, кто может видеть или менять определённые части кода.
- **Линейная модель работы команды.** Для небольших команд с простым линейным процессом разработки (без активного использования веток и слияний) простая модель SVN может быть понятнее и не требует привыкания к распределённой модели Git.
- **Устаревшая инфраструктура/legacy-проекты.** Многие старые корпоративные системы, CI/CD-пайплайны и инструменты уже завязаны на SVN, и миграция на Git может быть дорогой и рискованной.
- **Простота модели для новичков.** Линейная, централизованная история изменений в SVN иногда легче для понимания начинающими, чем распределённая модель с локальными и удалёнными ветками, staging-областью и т.д.
